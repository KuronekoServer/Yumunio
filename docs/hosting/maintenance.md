# 更新・バックアップ・復旧

[ホスティングの入口](README.md) / [困ったとき](troubleshooting.md)

## 更新の前に

使用中のバージョン・Composeファイル・公開URL・DBと添付の保存先を記録し、復旧できるバックアップを用意します。更新先のリリースにスキーマ変更の案内があれば、その手順を確認してください。新規導入の初期化と既存データのマイグレーションは用途が異なります。

通常のコンテナー更新は、現在と同じフォルダー、環境ファイル、ボリューム、Composeファイルの組み合わせを使います。

```sh
docker compose pull
docker compose up -d
docker compose ps
```

同梱HTTPSを使っている場合は、各コマンドに `-f compose.yaml -f compose.https.yaml` を付けます。ソースビルドの場合は [Dockerの案内](docker.md#ソースからビルドする)を使います。バージョンを固定する場合は `.env` の `YUMUNIO_IMAGE` を指定し、更新前のタグ・ダイジェストも記録します。

## 保存するもの

| 構成 | 保持する対象 |
| --- | --- |
| 標準Docker | `yumunio-data` ボリューム全体、`.env`、使用したComposeファイル |
| 同梱Caddy | 追加で `yumunio-caddy-data`・`yumunio-caddy-config` |
| 外部DB・S3互換保存 | DBの整合したバックアップ、非公開ファイル、元の接続情報・内部の認証情報 |
| Workers | D1、非公開R2、元のWorkerの秘密設定、バインディングと公開URL |

Dockerの `.data/instance-secret` に相当する内部情報と、Workerの `YUMUNIO_INSTANCE_SECRET` は更新時に再生成しません。これらは暗号化された設定の復旧にも必要です。組み込みバックアップは環境変数の秘密値をすべて保存する仕組みではないため、元の設定も別に保持します。

## バックアップを作る

ワークスペースのエクスポートは内容の持ち出しに使えます。サーバー全体のDB・アカウント・非公開添付を復旧する用途では、[詳細設定](../../deploy/advanced.env.example)のバックアップ保存先と暗号化を設定し、管理画面の `/backups` から対象と保存先を確認してください。バックアップの作成結果と検証結果を確認し、別の空の復旧先でも動作を試します。

SQLiteを手動で保管する場合は、アプリを停止して保存ボリューム全体の整合したコピーを取得します。動作中のSQLiteファイルだけを単純にコピーする方法にはしません。DBと添付を別々の時点で取得すると、参照の整合が失われることがあります。

WorkersではD1のエクスポートだけではR2の添付や秘密設定を保管できません。復旧するDB・ファイル・内部情報を同じ構成として揃えます。

## 復旧・切り戻し

元の環境を保持したまま、別の空の保存先へ復旧します。CLIの [backup.mjs](../../apps/server/cli/backup.mjs) は空の対象への復旧を明示する方式です。既存の稼働DBへ上書きする手順として使いません。

アプリのイメージを以前の版へ戻すだけでは、変更済みDBのスキーマが戻るとは限りません。リリースごとの対応範囲と、更新前に保管した整合したDB・添付を確認して復旧します。
